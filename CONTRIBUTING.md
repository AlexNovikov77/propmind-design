# Как вносить изменения

1. Сформулировать конкретный результат и критерии приёмки в GitHub Issue. При временной недоступности записи использовать docs/BACKLOG.md.
2. Создать ветку от актуального main: feat/…, fix/… или chore/….
3. Реализовать один понятный результат. Реальные клиентские документы и заполненные реестры в публичный репозиторий не добавлять.
4. Выполнить npm test, npm run check и git diff --check. Для изменения поведения интерфейса пройти браузерный сценарий и проверить телефон.
5. Открыть PR: проблема, поведение после изменения, проверки и ограничения. Связать с задачей.
6. После успешных проверок и согласованного результата выполнить merge без переписывания существующей истории. Проверить опубликованный сайт и обновить статус задачи.

Развивать существующую структуру. Для новой библиотеки должны быть понятны необходимость, лицензия и влияние на размер/сборку. Правила работы с замечаниями держать в assets/registry.mjs, без зависимости от DOM. Изменение формата экспортируемых данных должно иметь версию и миграцию.

Концепты остаются макетами, пока интеграция не проверена на реальном API. Демо-данные обозначаются явно. Успешная сборка не означает проверки бизнес-результата или безопасности эксплуатации объекта.

Владельцы, готовность, защита main и релизы описаны в [DEVELOPMENT](docs/DEVELOPMENT.md). Dev-зависимости устанавливаются через npm ci, lock-файл обновляется вместе с package.json. Полный браузерный сценарий обязателен в CI; визуальные изменения проверяются на компьютере и телефоне.
